# 可被搜索性诊断器 · Searchability Kit

> **招聘方在平台上按关键词找人。你的简历里没有那些词，就等于不存在。**

上传「简历 + 目标岗位 JD」，输出：**招聘方在找哪些词、你字面命中了几个、漏掉的哪些只是措辞没对上、哪些是真没做过**，并可直接导出一份改写后的 Word 简历。

- 纯本地运行，服务只监听 `127.0.0.1`，局域网访问不到
- **零第三方 Web 框架、零前端依赖**（Python 标准库 + 原生 JS，页面无任何外链）
- 唯一会联网的地方：调用你自己配置的模型 API

---

## 为什么做这个

一位招聘负责人的原话：

> 「LinkedIn 只给你看几百个，剩下几千个你压根懒得点进去看。」

反过来对求职者意味着：**如果你的简历没命中招聘方在搜的词，你在他们眼里根本不存在——不是不够格，是从来没被搜到过。**

而这件事求职者永远看不到，因为**招聘方的搜索词是黑箱**。

市面上几乎所有简历工具都在优化「内容质量」（写得好不好）。这个工具做的是另一个维度：**可被搜索性**（会不会被找到）。

---

## 核心指标：精确覆盖 vs 宽松覆盖

不看单一分数，而看两个数，以及它们之间的差。

| 指标 | 含义 |
|---|---|
| **精确覆盖** | 招聘方**字面**能不能搜到你的简历 |
| **宽松覆盖** | 把你的经历换成招聘方的说法之后，能达到的上限 |
| **差额** | **只换个说法就能拿到的分** —— 这才是可执行的部分 |

一个真实案例（1 份简历 × 6 份真实 JD）：某份简历对目标岗位的精确覆盖从 **25% → 83%**，
而**内容一字未改，全是措辞**。这就是差额的意义。

## 快速开始

### 1. 准备

- Python 3.10+
- 一个模型 API Key（默认 DeepSeek）

### 2. 填 Key

首次双击 `启动.bat` 时，它会自动从 `sk/apikey.example.txt` 生成 `sk/apikey.txt` 并用记事本打开，
把 Key 粘进去（只粘 `sk-` 开头那一串，不要引号、不要空格），保存关闭，再双击一次。

Key 申请：https://platform.deepseek.com

### 3. 启动

双击 `启动.bat` → 浏览器自动打开 `http://127.0.0.1:8765/`

### 4. 用

两个上传框分别放**简历**和**JD**，点「开始诊断」。

支持格式：`pdf` `docx` `txt` `md` `png` `jpg` `webp`

> **图片需要额外配置视觉模型**（DeepSeek 的对话模型不支持看图）。
> 把 `sk/apikey.txt` 里【方案一】智谱 GLM-4V-Flash 那三行的 `#` 去掉即可，该模型免费。
> 不配也行：txt / pdf / docx 全部正常。

### 命令行也能用

```bash
python sk/main.py --resume inputs/resume.txt          # 跑 inputs/ 下所有 JD
python sk/selftest.py                                 # 离线自检，不需要 Key
python sk/compare.py --a 旧版简历.txt --b 新版简历.txt  # A/B 对比覆盖率变化
```

## 架构

```
JD ──┐
     ├─→ [规则库]  抽短词 ──────────────┐   算分用（可复现、有锚点）
     ├─→ [LLM]    抽 JD 原话长短语 ─────┤   只做展示与建议来源，不进分母
     │                                  ▼
简历 ─→ [脱敏/解析] ─→ [代码] 精确匹配 ─→ 命中/次数/上下文
                                  │
                                  ▼
                          [LLM] 生成改写建议 + 锚点
                                  │
                          [代码] 逐字复核锚点
                                  │
                          报告 / 网页 / Word
```

**分工是刻意的**：LLM 负责「理解」，代码负责「判定」，LLM 只基于代码算出的结果给建议。
每条「命中 / 未命中」都能复现、能审计。

## 踩过的三个坑（也是这套架构的由来）

### 坑 1：让 LLM 直接用 JD 原话当关键词，指标被打崩

模型抽的是 `技术方案撰写`、`客户需求分析` 这类复合短语，而简历里写的是 `方案讲解`、`需求调研`。
字面全对不上 —— 6 份 JD 里有 4 份精确覆盖直接归零。

**结论：模型词不能进分母。** 它贴 JD 原话、贴近真实搜索，但字面几乎不可能命中。

### 坑 2：报告自相矛盾

第三段（规则库判定）说「这个关键词真缺，不要加」，第四段（模型判定）说「可以补」。
根因是两套判定用了不同的锚点来源。

**结论：v2 模式下判定口径必须统一到模型 + 锚点复核。**

### 坑 3：修了别名映射，数字还是偏低

让模型自己给出「简历里可能怎么写」的等价说法，数字从 0% 回到 15–64%，仍低于规则库的 75–94%。

到这里才想明白：**问题不是别名不够好，是让 LLM 越界了。**

**最终架构：规则库算分，模型理解与建议。** 报告里每个关键词都标了 `来源：规则库 / 模型`。

## 局限（写在明处）

1. **锚点复核是字面级的**：能拦住「模型编造简历原文」，但拦不住「拿真原文硬贴不相关的意思」。
   例如模型可能拿「写文档」去支撑「培训」。这层语义判断必须人来做。
2. **词库覆盖有限**：规则库决定分母，遇到新行业会漏词，需要补 `kwlib.py`。
3. **图片依赖外部视觉模型**：DeepSeek 无视觉能力，需要另配 Qwen-VL / GLM-4V。
4. **只优化「被看见」，不解决「被录用」**：关键词帮你进候选池，能不能拿 offer 取决于经历本身。

> 所有建议都建立在「你确实做过这件事」的前提下。简历里找不到依据的词，工具会直接判「不要补」——
> 硬加进去，面试第一句话就穿了。

## 隐私

- 服务只监听 `127.0.0.1`
- 页面零外链（无 CDN、无字体服务、无统计脚本）
- 上传文件存 `web/uploads/`，导出 Word 存 `web/outputs/`，缓存存 `sk/_cache/` —— 三处均已 gitignore
- 除调用你自己配置的模型 API 外，无任何网络请求

## 技术栈

Python 3.10+ 标准库（`http.server` / `urllib` / `zipfile` / `re`）+ 原生 HTML/CSS/JS。

**没有 Flask、没有 FastAPI、没有 React、没有 LangChain、没有 openai SDK、没有 python-docx。**
唯一可选依赖是 `pdfplumber`（只用于读 PDF）。
